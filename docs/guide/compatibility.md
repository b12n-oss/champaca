# What matches the JVM

Champaca runs the JDK's own classes, so most behavior is the JVM's by construction. Where the runtime supplies something itself (the natives, the bootstraps it compiles, the threads), it was checked against HotSpot, and the test named in each item below pins what was checked. [limitations](limitations.md) lists what's missing or different.

- **javac's bootstraps are compiled, not run.** The translator spots `LambdaMetafactory`, `ObjectMethods`, `makeConcatWithConstants` and the pattern-switch bootstraps and generates the code directly. Any other `invokedynamic` runs its bootstrap method for real, once per call site (`test/java/IndyCheck.expected`, from a class `test/gen/IndyCheckGen.java` writes). A dynamic constant, method handle or method type resolves once per constant-pool entry, however many instructions name it, and a resolution that fails with a `LinkageError` fails the same way each later time without running its bootstrap again. The `BootstrapMethodError` texts are the JDK's (`test/java/CondyCheck.java`).
- **Reflection matches the JVM, short of a few gaps.** Methods, fields, constructors, `invoke`, `newInstance` and field get/set work (`test/java/Reflect.java`), and they check the receiver and each argument or value as the JVM does, widening a primitive but never narrowing it and refusing to set a final field, with the JDK's messages (`test/java/ReflectArgCheck.java`, `test/java/FieldArgCheck.java`). `invoke`, a method handle and a plain call select the method the JVM selects: a private method is its own, and a package-private one is overridden only from its run-time package (`test/java/DispatchCheck.java`). So do annotations with their defaults, generic signatures, and member, local and anonymous classes (`test/java/AnnotationCheck.java`). So do record components, parameter names, checked-exception lists and type annotations (`test/java/RecordCheck.java`), and Jackson binds records. Sealed classes and interfaces answer `isSealed` and `getPermittedSubclasses` (`test/java/SealedCheck.java`). An annotation is an instance of a generated class, not a `java.lang.reflect.Proxy`, though its `toString`, `equals` and `hashCode` are the JDK's. Field access checks access control as `Field.get` does on the JVM (`test/java/FieldAccessCheck.java`).
- **Threads take turns.** Each Java thread is a real thread, and `synchronized`, `wait`/`notify`, `sleep`, `interrupt`, executors and `CompletableFuture` all work (`test/java/ThreadCheck.java`), and the main thread ends when `main` returns, so another thread's `main.join()` returns and a shutdown hook sees it terminated (`test/java/MainExitCheck.java`), but one global lock lets only one of them run Java code at a time. So threads give correct results and no speedup. Virtual threads run as platform threads, the JDK's fallback when continuations aren't there, so they give the JVM's results without the JVM's cheap concurrency (`test/java/VirtualThreadCheck.java`).
- **Method handles cover the combinator surface.** The `Lookup.find*` and `unreflect*` methods, `invokeExact`, `invoke`, `invokeWithArguments`, `asType`, `bindTo`, the spreaders and collectors, the array element handles, the invokers and the `MethodHandles` combinators from `zero` to `tryFinally` and the loop builders work with the JVM's conversions and exception texts (`test/java/MethodHandleCheck.java`, `test/java/MethodHandleCombinatorCheck.java`, `test/java/LoopHandleCheck.java`). Lookups check access as the JVM's do, with its messages: the class named, the member's modifiers against the lookup, `findSpecial`'s caller, and a protected method's receiver narrowed to the lookup class (`test/java/LookupAccessCheck.java`). `invokeExact` insists on the exact type, as the JVM does (`test/java/ExactCheck.java`).
- **VarHandles work for fields and arrays.** `findVarHandle`, `findStaticVarHandle`, `unreflectVarHandle`, `arrayElementVarHandle`, `byteArrayViewVarHandle` and `byteBufferViewVarHandle` return handles that support the same access modes as the JVM's, throwing `UnsupportedOperationException` for the rest (`test/java/VarHandleCheck.java`, `test/java/VarHandleModes.java`), so `java.util.concurrent.atomic` and `ConcurrentHashMap` run. Memory-ordering modes all act the same, which is safe while one thread runs Java at a time. The six coordinate combinators (`insertCoordinates` and friends) work too (`test/java/VarHandleCombinatorCheck.java`); `byteBufferViewVarHandle` makes a handle whose every access throws `UnsupportedOperationException`.
- **Memory segments, downcalls and upcalls work.** `MemorySegment`s over Java arrays and over native memory from an `Arena` (confined, shared, auto or global) read and write through their layouts: `get` and `set`, `getAtIndex`, a layout's `varHandle` with every access mode the JDK gives it, layout paths into structs and sequences, `copy`, `fill`, `mismatch`, strings. Bounds, alignment, read-only, closed and wrong-thread accesses fail with the JDK's exceptions and texts (`test/java/SegmentCheck.java`), since the access code is the JDK's own. An access costs about 0.3 to 0.5 us, against an array element's few nanoseconds. `Linker.nativeLinker()` calls C functions: from the default lookup (libc, libm), `SymbolLookup.libraryLookup` or `System.loadLibrary` with `loaderLookup`, with integers, floating point and addresses, structs and unions by value, variadic arguments, `errno` capture and critical calls over heap arrays, and the JDK's checks and texts for the rest (`test/java/ForeignCheck.java`). A call takes 0.25 us when it's critical and 0.6 to 1.3 us when it gives the global lock up so other threads run meanwhile, against HotSpot's 5 to 25 ns. Upcalls work too: `Linker.upcallStub` turns a method handle into a C function pointer, so `qsort` can sort with a Java comparator. Upcalls take and return structs, they come from several Java threads at once, and they come from threads C started, which get a daemon `Thread-N` each, as on HotSpot. A target that throws ends the process after printing its trace, as the JDK's own wrapper does (`test/java/UpcallCheck.java`). An upcall costs about 1 us, against HotSpot's 60 ns.
- **Files go through libc, on macOS and Linux.** `java.io`, `java.nio.file`, `FileChannel` (locks and memory maps included) and `java.util.zip` call libc and zlib through Chez's foreign interface, on real file descriptors (`test/java/FilesCheck.java`, `test/java/FileOutputCheck.java`). `struct stat` and its relatives are read through a table of offsets measured on each system: macOS (arm64 and x86_64) and Linux with glibc 2.33 or newer on arm64 and x86_64 (`ci/linux/layout.c` prints Linux's). Elsewhere, a BSD, musl, or a glibc older than 2.33 (which doesn't export `stat` itself), `java.nio.file` stops with an `UnsupportedOperationException` at its first use, while `java.io` streams still work. `ci/linux` has a Docker image that runs the suite and the libraries on Linux (`jolt linux`), and CI (`.github/workflows/ci.yml`) runs the battery there on GitHub's x86_64 and arm64 runners, and on macOS arm64. `Files.getFileStore` and `FileSystem.getFileStores` read the mount table, `getfsstat` on macOS and `/proc/mounts` on Linux (`test/java/FileStoreCheck.java`).
- **Stack traces are the JVM's.** `getStackTrace`, `printStackTrace`, `Thread.currentThread().getStackTrace()`, `StackWalker` and the source location `java.util.logging` infers give the same frames as the JVM, with file names and line numbers for your own classes from a class directory (`test/java/StackCheck.java`; a jar's classes get them with `CHAMPACA_LINES=all`, and without it a jar's inlined leaf method that throws from a check shows its caller's frame, [limitations](limitations.md#other-gaps)), and an uncaught exception prints its trace the way the JVM's default handler does. A JDK frame names its file but no line, because the startup cache keeps no inspector information for JDK code (with it, a warm start took 0.04 s longer and the cache grew by half). A native champaca wrote in Scheme has no frame, where the JVM prints `Native Method`.
- **The module system boots.** `ModuleLayer.boot()` holds the modules jlink resolved into the runtime image, so `ServiceLoader` sees the JDK's own providers: locale data (`1.234,50 €`, `jeudi 22 octobre`), the extended charsets (Shift_JIS, windows-1252), `ToolProvider`. A JDK class reports its named module, and reflection into a package it doesn't export fails as on the JVM. The application class loader is the system and context class loader, your classes report it and sit in its unnamed module, and a JDK class reports the loader its module is defined to (`test/java/ModuleCheck.java`). It costs a warm start about 0.07 s and a cold one five seconds ([performance](performance.md#the-startup-cache)).
- **Classes can be defined at run time.** `ClassLoader.defineClass` (bytes, or a `ByteBuffer` heap or direct), `Lookup.defineClass` and `defineHiddenClass` (with class data), and `Class.forName` through a loader of your own that defines on demand all work, so `java.lang.reflect.Proxy` does too: a proxy class is generated by the JDK's own `ProxyGenerator` and defined through the same native (`test/java/DefineCheck.java`). A defined class reports its defining loader and, for a hidden one, a name of the JVM's shape, `Name/0x<n>`. A class a loader defines may name others only that loader has, defining them from its `findClass` as ABCL's loader does: each is asked of it through `loadClass`, as the JVM resolves a reference through the referring class's loader, though here when the method naming it is first translated, except for an `ldc` of a class (a `Foo.class` literal), which resolves when it runs, as on the JVM ([limitations](limitations.md#other-gaps)). Reflection resolves a member's types through its declaring class's loader too (`test/java/LinkCheck.java`). One class table remains, so a name can be defined once across all loaders.
- **Class definitions are checked as HotSpot checks them.** A final superclass, an interface as the superclass, a class among the interfaces, an override of a final method, a class among its own supertypes, and a subclass that a sealed class or interface doesn't permit are refused with HotSpot's error and text. That holds from the class path, from a loader's bytes, from the library cache and at an instruction naming the class (`test/java/ClassDefCheck.java`, `test/java/SealedCheck.java`). The one gap is a hand-made lambda over a sealed interface, which is made where the JVM refuses it.
- **Object serialization works.** `ObjectOutputStream` and `ObjectInputStream` round-trip your classes and the JDK's, and the bytes are the JVM's: the same class descriptors, field order and computed `serialVersionUID`s. `writeObject`/`readObject`, `writeReplace`/`readResolve`, `Externalizable`, enums, records, arrays, shared references and serializable proxies work, a non-serializable superclass's no-arg constructor runs on deserialization as the specification asks, and a stream resolves class names through the first class loader on the stack that isn't a built-in one, as the JVM does, or through the application loader when jolt itself is the reader (`test/java/SerialCheck.java`, `examples/serialization.clj`).
- **TCP sockets work, over IPv4 and IPv6.** `Socket`, `ServerSocket`, blocking `SocketChannel`s, `HttpURLConnection` and `InetAddress` lookups call libc the way the file natives do, with timeouts, half-close, the socket options and the JDK's exception texts (`test/java/SocketCheck.java`). Sockets are dual stack as on the JVM: an IPv6 socket also reaches IPv4 peers, a server on the wildcard sees an IPv4 client as an `Inet4Address`, and lookups return both kinds of address in the JDK's order (`test/java/Ipv6Check.java`, the same on a Mac and in a Linux container). `-Djava.net.preferIPv4Stack=true` turns IPv6 off, as it does on the JVM. UDP works too: `DatagramSocket` and `DatagramChannel`, connected or not, blocking, with a timeout or under a selector, with the JVM's truncation, port-unreachable and close behavior (`test/java/DatagramCheck.java`). `NetworkInterface` lists every interface with its IPv4 and IPv6 addresses, an IPv6 one scoped to its interface (on a Mac all twelve matched the JVM's, order and prefixes included). The check covers the loopback interface, since the rest differ by machine, and on a Mac and in a Linux container every interface's flags, MTU, hardware address and address prefixes were compared by hand with the JVM's and matched. And `isReachable` tries TCP port 7 as the JDK does without root. Joining multicast groups is not there yet.
- **Child processes work.** `ProcessBuilder` and `Runtime.exec` start programs through `posix_spawn`, with pipes, files, discarded or inherited streams, a changed environment and working directory, and the JDK's PATH search, `/bin/sh` fallback for a script without `#!` and launch error texts. `waitFor` (with a timeout), `destroy`, `destroyForcibly`, `onExit` and `startPipeline` behave as on the JVM, and so do exit codes, a signal's included (`test/java/ProcessCheck.java`). A child gets SIGPIPE's default disposition and none of the parent's other descriptors, as a JVM's does.
- **Selectors work, and so does `java.net.http.HttpClient`.** `Selector` runs on the JDK's own `KQueue` selector on macOS and its `EPoll` one on Linux, so non-blocking `SocketChannel`s and `ServerSocketChannel`s, `Pipe`s, `wakeup`, interrupts and closing a selector from another thread behave as on the JVM, and `HttpClient`'s HTTP/1.1 requests, sent and sent asynchronously, go through its selector thread (`test/java/SelectorCheck.java`). HTTPS works through it too, with HTTP/2 negotiated, checked by hand against a public site on 2026-10-25 since the tests stay offline ([limitations](limitations.md#native-code)). A `select` that waits gives the GIL up.
- **What the VM reports matches.** `Thread.getAllStackTraces` and `enumerate` list the live threads, and another thread's stack reads as on the JVM, line numbers included, wherever it waits: in `sleep`, `wait`, `park`, a contended monitor or blocking I/O (`test/java/OtherStackCheck.java`). `ThreadMXBean` measures each thread's CPU time. Nests come from the class file's `NestHost` and `NestMembers` attributes, and an array class has its element's access. `Package.getPackage` answers for the JDK's loaded packages and for each package of yours once one of its classes has been asked for its package (`test/java/PackageCheck.java`). The default locale, `java.io.tmpdir` and `sun.java.command` are what the JVM gives on the same machine (`test/java/VmCheck.java`).
- **No native libraries.** A JDK library load (`zip`, `net`, `management`) is a no-op, since its natives are Scheme code (or libc calls) here. A Java library's own JNI code can't load, and a JDK native champaca hasn't written yet throws `UnsatisfiedLinkError`, as the JVM does for an unloaded one, so a program can catch it (`test/java/NativesCheck.java`).
- **`sun.misc.Unsafe` doesn't warn.** `sun.misc.unsafe.memory.access` is `allow`, so Caffeine and Guava, which still use it, run without the JDK's warning on stderr.
