# Limitations

Champaca is a spike. It runs the JDK's own code, but only along the paths its tests and the nine checked libraries (commons-lang3, commons-lang 2.4, gson, jsoup, Jackson, Caffeine, Guava, SLF4J, SnakeYAML) have exercised. Code outside those paths can hit a missing native or one of the shortcuts below. This page lists the ones known so far, roughly in the order a real program meets them.

## Threads take turns

Threads work, but they don't run in parallel. Each Java thread is a real Chez thread, and one global lock lets only one of them run Java code at a time ([how-it-works](how-it-works.md#threads)). A program that uses threads for correctness (a background worker, a producer and a consumer, an executor) behaves as on a JVM. One that uses them for speed gets none.

Some details follow from that. A thread that loops without calling anything gives the lock up every thousand backward branches once another thread is waiting, so a spin-wait ends, but a long recursive computation with no loop in it can keep the others waiting until it returns. So can a `MemorySegment.mismatch` over a long segment, or a Vector API load or store through one: those keep the lock until they finish, so that no thread is in the middle of reading a shared arena's memory when another closes it, which the JVM ensures with a handshake. A thread waiting on I/O gives the lock up: reading standard input, a pipe, a FIFO or a terminal, writing to a full pipe, opening a FIFO and `Files.copy` from a pipe (`test/java/BlockingIoCheck.java`), and taking a blocking file lock. Writes to standard output and error still hold it, so a program whose output pipe fills up stops until the reader catches up. Closing a socket, a channel or a FIFO from another thread wakes a thread blocked on it, with the JVM's exception (`SocketException: Socket closed`, `AsynchronousCloseException`), and interrupting a thread blocked in a channel read gives `ClosedByInterruptException` (`test/java/SocketCheck.java`). A thread waiting for a blocking file lock is the exception: see [other gaps](#other-gaps). VarHandle and `Unsafe` memory-ordering modes all behave alike, which is safe for the same reason. Virtual threads run, but without continuations: the JDK falls back to its `BoundVirtualThread`, one platform thread per virtual thread, so `Thread.ofVirtual()`, `startVirtualThread` and `newVirtualThreadPerTaskExecutor` give the JVM's results and `isVirtual` is true, but each costs what a platform thread costs and they take turns like the others (`test/java/VirtualThreadCheck.java`). `getState` says what a thread waits for as HotSpot does: `TIMED_WAITING` while it sleeps, `WAITING` or `TIMED_WAITING` in `Object.wait` and `LockSupport.park`, `BLOCKED` while it waits to enter a monitor, and `RUNNABLE` while it waits on I/O (`test/java/OtherStackCheck.java`).

## `invokedynamic` and method handles

Both work, with a few gaps. The bootstraps javac emits are compiled directly: lambdas, records, string concatenation and pattern switches. Any other bootstrap method runs for real, once per call site, and a dynamic constant once per constant-pool entry ([how-it-works](how-it-works.md#method-handles)).

Method handles come from the `Lookup.find*` and `unreflect*` methods, and `invokeExact`, `invoke`, `invokeWithArguments`, `asType`, `bindTo`, `asSpreader`, `asCollector` and the `MethodHandles` combinators work on them: `zero`, `empty`, `constant`, `identity`, `insertArguments`, `dropArguments`, `filterArguments`, `filterReturnValue`, `foldArguments`, `collectArguments`, `guardWithTest`, `permuteArguments`, `explicitCastArguments`, `catchException`, `throwException`, `tryFinally`, the array element handles and the three invokers, with the JVM's conversions and exception texts (`test/java/MethodHandleCombinatorCheck.java`). `Lookup.bind`, `findVirtual` on `MethodHandle.invoke` and `invokeExact` or on a `VarHandle` access mode, and the two VarHandle invokers work too (`test/java/InvokerCheck.java`). The loop builders (`loop`, `whileLoop`, `doWhileLoop`, both `countedLoop`s, `iteratedLoop`) run the JDK's own Java, so its checks and texts are the JVM's, and the loop it builds runs in Scheme as the JDK's interpreted form runs it (`test/java/LoopHandleCheck.java`). `invokeExact` checks the call's type against the handle's exactly, as the JVM does, so a subtype, a boxed value or a widened result is `WrongMethodTypeException` with the JDK's text (`test/java/ExactCheck.java`). `asType` refuses an impossible conversion when the handle is built, with the JVM's `WrongMethodTypeException` text. `explicitCastArguments` converts as the JVM's does: it narrows, turns a boolean into 1 or 0 and any number into a boolean by its low bit, reads a null as zero, and doesn't check a cast to an interface (`test/java/ExplicitCastCheck.java`). Lookups don't check access either, though a field one finds is resolved as the JVM resolves it (superinterfaces included), with the JDK's texts when it isn't there, is static where it shouldn't be or the reverse, or is final for a setter (`test/java/FieldLookupCheck.java`). A pattern switch label that javac builds from a dynamic constant other than a primitive class, a boolean constant or an enum constant fails to translate.

VarHandles work too: `findVarHandle`, `findStaticVarHandle`, `unreflectVarHandle`, `arrayElementVarHandle`, `byteArrayViewVarHandle` and `byteBufferViewVarHandle` (`test/java/ByteBufferViewCheck.java`), which is what `java.util.concurrent.atomic` and `ConcurrentHashMap` need. Each supports the access modes the JVM's would, and the rest throw `UnsupportedOperationException`. So a `final` field is read-only, a `float` has no bitwise updates, and a `byte[]` view takes only plain `get` and `set`, as on JDK 25. A call site's types are converted as `asType` would, which means widening, boxing and unboxing but never narrowing (an `int` passed for a `short` throws `WrongMethodTypeException`), and a handle from `withInvokeExactBehavior` rejects a call whose types differ with `WrongMethodTypeException`. The six coordinate combinators work (`filterValue`, `filterCoordinates`, `insertCoordinates`, `permuteCoordinates`, `collectCoordinates`, `dropCoordinates`), with the JVM's construction-time checks and messages; a derived handle supports the modes its target does. Their filters aren't screened for checked exceptions: the JVM refuses a direct handle whose method declares one and wraps any other handle so a checked exception becomes `IllegalStateException`, and champaca does neither. `byteBufferViewVarHandle` returns a handle, but every access through it throws `UnsupportedOperationException`. A reference passed where the handle wants a primitive is cast when the access runs, so a `String` for an `int` throws `ClassCastException`, where the JVM refuses the call with `WrongMethodTypeException` before it runs.

Memory segments work, over Java arrays and over native memory from any kind of `Arena`. A layout's VarHandle (`ValueLayout.varHandle`, a layout path's, the one behind `MemorySegment.get` and `set`) holds the JDK's own `SegmentVarHandle`, and each access mode calls the JDK's Java for it, so bounds, alignment, read-only, closed-arena and wrong-thread checks run as written, with the JDK's exceptions and texts, and an unaligned layout's handle takes only plain `get` and `set`, as on the JVM (`test/java/SegmentCheck.java`). That makes an access slow: summing 100,000 ints through `getAtIndex` took 46 ms on a heap segment and 33 ms on a native one, against 0.3 ms over the array, where HotSpot's are about equal. Downcalls work through `Linker.nativeLinker()`, with the JDK's checks and texts, structs and unions by value, variadic calls, `errno` capture, and critical calls that see a heap array (copied into native memory for the call and back after it), against HotSpot (`test/java/ForeignCheck.java`). A call costs 0.25 us when critical and 0.6 to 1.3 us otherwise, against HotSpot's 5 to 25 ns, since a call that isn't critical gives the global lock up while it runs in C. Upcalls work: `Linker.upcallStub` gives C a function pointer that calls a method handle, with the JDK's checks (a target declaring a checked exception is refused) and its handling of a target that throws, which prints the trace and ends the process with status 1 (`test/java/UpcallCheck.java`, `test/mainsel/UpcallThrow.java`). Structs pass and return by value, in registers or through memory, and arguments past the registers come from the stack where the JDK's calling sequence puts them, a struct the ABI passes there included, on macOS and Linux, arm64 and x86_64. An upcall can come from a thread C started, which becomes a daemon `Thread-N` in group `main` for that thread's life, as HotSpot attaches it. Each upcall costs 0.8 to 1.5 us against HotSpot's 60 ns, most of it taking and giving back the global lock and going through the JDK's binding handles. An upcall from a function called through a critical downcall isn't supported here or on HotSpot. On macOS arm64, Chez Scheme 10.4.1 places some arguments that go on the stack (once the registers are used up) where Apple's ABI doesn't. A struct of 16 bytes or less that isn't all floats or all doubles starts on an 8-byte boundary and takes a multiple of 8 bytes there, where Chez packs it like a scalar, and an argument that follows one ending at an odd offset can start a few bytes early (a struct of three floats, a `char`, then another such struct), which moves plain scalars too (three `char`s, then a `short`). A signature where any argument would move is refused with `UnsupportedOperationException` rather than called with the wrong bytes. Linux passes stack arguments in 8-byte slots, so these placements are right there, and `ForeignCheck` prints HotSpot's output on Linux arm64. On Linux x86_64 the placements are right too, but Chez copies a struct passed on the stack in pieces and writes each piece as a whole 8-byte word, so when the struct's size is 3, 5, 6 or 7 bytes past a multiple of 8 the copy runs over the start of the next argument (a `short` after a 3-byte struct arrived as 0). Such a signature is refused with `UnsupportedOperationException` there, and `ForeignCheck` prints HotSpot's output on GitHub's x86_64 runner. Chez has the fix too (in [cisco/ChezScheme#1091](https://github.com/cisco/ChezScheme/pull/1091), jolt's patch 0007), with the same catch as below: a jolt built on an unpatched system Chez still has the bug. On both systems, a struct over 16 bytes that comes after the registers are used up, which goes by pointer on the stack, makes Chez fail to compile the call at all, and that's an `UnsupportedOperationException` too. jolt 0.8.24 carries Chez patches that fix both ([jolt#1502](https://github.com/jolt-lang/jolt/pull/1502), from [cisco/ChezScheme#1091](https://github.com/cisco/ChezScheme/pull/1091)), but only when its build compiles its own Chez: `make build` uses a system Chez such as Homebrew's as it is. Champaca can't tell the two apart, so it refuses these signatures on any jolt. On 3066 generated signatures of eight `int`s (and eight `double`s, in some) followed by two or three mixed arguments, 650 would have been wrong; champaca refused 676, so 26 it could have made, and ran the rest right. A downcall handle's `invokeExact` converts its arguments as other handles do, rather than insisting on an exact type match.

## Reflection

Methods, fields, constructors, `Method.invoke`, `newInstance` and field get and set work. They check the receiver and each argument or value as the JVM does: a box for a primitive is unboxed and widened but never narrowed, a reference must be an instance of its type, and anything else is the JDK's `IllegalArgumentException`, message included. `getInt`, `setLong` and the other typed accessors take only a primitive field the value widens to or from. Setting a final field throws `IllegalAccessException` as on the JVM: a static final field always, a record's or a hidden class's always, any other only until `setAccessible(true)`. A caller-sensitive method such as `Class.forName`, `Method.invoke` or `setAccessible`, called through `Method.invoke`, sees the caller the JVM would give it. So do annotations with their defaults, generic signatures, and member, local and anonymous classes. Record components, parameter names (real ones when the class was compiled with `javac -parameters`, else `arg0`, `arg1` as on the JVM), checked-exception lists and type annotations match the JVM's too, which is what Jackson needs to bind records. An annotation is an instance of a generated class rather than a `java.lang.reflect.Proxy`, so `Proxy.isProxyClass` says false for it, but its `toString`, `equals` and `hashCode` are the JDK's own. Field access through reflection ignores access control. `Class.getPackage` gives one `Package` per name. A classpath package carries the version attributes of the manifest of the jar its first loaded class came from, as the JVM's class loaders define it, so a package split over two jars reads the same as on the JVM. A JDK package belongs to its named module, so it reports `isSealed` and no version, as on the JVM. Some differences remain. Sealing isn't enforced, so a sealed package split over two jars loads instead of throwing `SecurityException`. A jar whose manifest the JDK would refuse gets a warning on stderr and its classes load without version information, where the JVM fails to load them. A lambda's class is `champaca/$$Lambda$...`, shared by every call site with the same interface, so its package is `champaca` rather than its caller's. `Package.getPackage(String)` and `Package.getPackages()` find a JDK package of the boot loader once a class of it has loaded, as on the JVM, and it's the same `Package` that `Class.getPackage` gives. A package of your own classes isn't found that way, though, and `ClassLoader.getDefinedPackage` finds none of your packages either. A package of a platform-loader module such as `java.sql` is found only once something has called `getPackage` on one of its classes, where the JVM's platform loader defines it as it loads the first class. Nests come from the `NestHost` and `NestMembers` attributes, checked as JVMS 5.4.4 asks (the host loads, is in the same package and lists the class), and a hidden class defined as a nestmate joins its lookup class's nest. So `getNestHost`, `getNestMembers` and `isNestmateOf` answer as on the JVM, and a class file older than Java 11 is its own nest host there too. Sealed classes and interfaces answer `isSealed` and `getPermittedSubclasses` as on the JVM, and a class one of them doesn't permit (outside its module, a non-public one outside its package, or not listed) fails to load with HotSpot's `IncompatibleClassChangeError`. One case isn't refused: a lambda for a sealed interface, which javac never emits but hand-made bytecode can, is made where the JVM throws. `getDeclaredClasses` still returns an empty array.

## Native code

A JDK library load (`zip`, `net`, `management` and so on) is a no-op, because those natives are Scheme here. Any other library loads as on the JVM, from `java.library.path` or by `System.load`'s absolute path, so `SymbolLookup.loaderLookup()` finds its symbols. Its JNI code can't run: a library with a `JNI_OnLoad` is refused with `UnsatisfiedLinkError`, and a Java `native` method the library implements stays missing. A native champaca hasn't written yet throws `UnsatisfiedLinkError` too ([debugging](debugging.md#a-missing-native)), so a library's try/catch around an optional feature works as on the JVM, and a program that needs the native stops there. The ones known to be missing, roughly in the order a library meets them:

- Sockets work over IPv4 and IPv6, through libc: `Socket`, `ServerSocket`, blocking `SocketChannel`s, `HttpURLConnection` and `InetAddress` lookups. Selectors work, and with them non-blocking channels and `java.net.http.HttpClient`. `jolt test` checks HTTP/1.1 against a server in the same process; HTTPS, over HTTP/1.1 and over HTTP/2 (the response reported `HTTP_2`, so the server negotiated it), and `HttpsURLConnection` were checked by hand against a public site (`https://example.com`, 2026-10-25), since the tests need no network. In two warm runs that day the first HTTPS request took 3.0 and 3.1 s, against 0.2 to 0.4 s on the JVM, and a second client's request 0.4 to 0.5 s. UDP works over both (`DatagramSocket`, `DatagramChannel`), but a socket can't join a multicast group (`MulticastSocket.joinGroup` and `DatagramChannel.join` stop at a missing native). `NetworkInterface` reads `getifaddrs` for both families; the JDK reads Linux's IPv6 addresses from `/proc/net/if_inet6` instead, so their order within an interface can differ there. A Linux alias such as `eth0:1` is listed as an interface of its own, where the JVM makes it a virtual sub-interface of `eth0`. `InetAddress.isReachable` always tries TCP port 7, as the JDK does when it can't open a raw socket; run as root, the JVM sends an ICMP echo instead, so a host that drops port 7 silently but answers ping is reachable there and not here. Pending urgent data isn't discarded, and the extended options of `jdk.net` report themselves unsupported. `InetAddress.getLocalHost()` on a Mac whose hostname the resolver doesn't know (a home network, say) answers with the interfaces' IPv4 addresses, the loopback left out unless it's all there is, as the JDK's own macOS code does; on Linux the JDK has no such fallback and neither has champaca.
- Child processes start through `posix_spawn` whatever `jdk.lang.Process.launchMechanism` says, so the JDK's `jspawnhelper` never runs; what a program can see matches the JVM ([how-it-works](how-it-works.md#natives)). `ProcessHandle.Info` is empty: its command, arguments, user, start time and CPU time are all unknown. With no start times, a `ProcessHandle` can't tell its process from a later one that reused the pid, so `destroy` on a handle from `ProcessHandle.of` whose process is gone signals whatever runs under that pid now, where the JVM refuses; a `Process` is safe, since it stops signalling once it has seen its child exit. `ProcessHandle.children()` and `descendants()` stop at a missing native. Under Docker's x86_64 emulation on an arm64 Mac, a script without `#!` exits 127 instead of running through `/bin/sh`, because the emulated `posix_spawn` doesn't report that `exec` failed; natively it runs.
- A stack trace lists translated methods only: a native champaca wrote in Scheme has no frame, where the JVM prints one as `Native Method`. JDK frames carry no line numbers, only the file, since the startup cache keeps no inspector information for JDK code ([performance](performance.md#exception-handlers)), and by default neither do the frames of classes from jars or of classes a loader of the program's own defines, which `CHAMPACA_LINES=all` gives lines at about the memory their code takes ([performance](performance.md#memory)). One more thing goes with the lines: a method of such a class that calls nothing and throws from one of champaca's own checks (a division by zero, an array index, a cast, an array's size) while inlined into its caller shows the caller's frame where the JVM shows its own, since without the information Chez folds the inlined code into the caller's; `test/libcache/StackCheck-lines-off.expected` has the shape, and `CHAMPACA_LINES=all` restores the frame along with the lines, as does `CHAMPACA_BT=1`, whose wrappers keep the inlined code apart. Reflection's own frames differ in name (`DirectMethodHandleAccessor$NativeAccessor.invoke` here, `DirectMethodHandleAccessor.invoke` on the JVM). Another thread's stack (`Thread.getStackTrace()`, `Thread.getAllStackTraces()`) starts at the Java method that blocked: the JVM shows the native under it as well (`Thread.sleep0`, `Object.wait0`), which has no frame here, as above. `StackWalker`'s `SHOW_HIDDEN_FRAMES` option doesn't bring the hidden frames back.
- `java.management`: the Runtime, Memory, OperatingSystem and ClassLoading beans answer, and `ThreadMXBean` counts and lists threads. Its CPU times are measured for any live thread the way HotSpot measures them (`thread_info` on macOS, the thread's CPU clock and `/proc` on Linux). The thread lists hold the threads Java started and `main`: a jolt thread that called in isn't listed, and there are no JVM system threads such as `Reference Handler`. `ThreadInfo` stops at `getThreadInfo1` and thread dumps at `dumpThreads0`; `findDeadlockedThreads` says it's unsupported, as the JDK does when the VM reports no support, while `findMonitorDeadlockedThreads` stops at its native; the garbage collector and memory pool lists are empty. Memory figures are Chez's own heap counters, the same ones `Runtime.totalMemory()` and `freeMemory()` report. The operating system bean is `jdk.management`'s, as on the JVM: its host CPU counts and process CPU time are real, and its memory and swap sizes, CPU loads and file descriptor counts are -1, which its contract allows for what isn't measured.
- Classes defined at run time (`ClassLoader.defineClass`, `Lookup.defineClass` and `defineHiddenClass`, `java.lang.reflect.Proxy`) join the one class table, so a name can be defined once: a second loader defining a class of the same name gets `LinkageError` where the JVM gives each loader its own, and the application loader never loads the classpath's copy of a name another loader defined.

## The calling API

- `init!` takes effect once per process. A second call, with a different `:classpath` or `:preview` or not, does nothing.
- Until `save-cache!` runs, each JDK method the process compiles keeps its generated source in memory (a few KB per method) so a save can write it. A long-lived program should call `save-cache!` once its working set is warm, which also empties that list.
- The user classpath is searched before the JDK's modules, the reverse of Java's order.
- Every conversion copies. A Java method that changes a collection you passed it changes the copy, and a big collection is copied again on each call ([data-conversion](data-conversion.md#conversions-copy)).
- A vector passed to a plain `Object` parameter becomes an array, not a `List`.
- A Java object prints as `#object[:object]` in jolt. Use `ldk/to-string`.
- A jolt error that leaves one of your fns through Java is a plain `java.lang.RuntimeException` to Java, where on the JVM it would be Clojure's own `ExceptionInfo`. Java code that catches every exception and only logs it, or retries, swallows your error the same way, as it would on the JVM.
- `proxy` puts its proxies in the application class loader. A `proxy` method left out of the map runs its interface's default body, and Java code of your own can call `InvocationHandler.invokeDefault` as on the JVM (`test/java/MethodHandleCombinatorCheck.java`).
- A Java string can hold a lone surrogate (half of a UTF-16 pair) and a jolt string can't, so one comes back to jolt with U+FFFD in its place. Inside Java nothing is lost: string constants, concatenation and `switch` keep the code units exactly.

An integer goes to a `byte` or `short` parameter, and a vector of them to a `byte[]` or `short[]`, only when no overload fits without narrowing, since jolt has no byte type to ask for one and Java never narrows an argument. So `ByteBuffer.wrap([1 2 3])` and `MessageDigest.update` take a vector, but where an `int` overload exists it wins, and an integer out of range for the type fits nothing. A `byte` is signed, so `0xCA` or `200` is out of range: write -54, or build the array with `HexFormat.parseHex` ([data-conversion](data-conversion.md#vectors-and-arrays)). `char` isn't narrowed this way: pass a character.

## Classes defined from jolt

- A class `define-class` made is defined once per process, since one class table holds every class. Evaluating the same definition again swaps in its new fns, but a new field, a new method key, another superclass or interface, or other annotations are refused. At the REPL, give the class a new name while you experiment, or restart the process.
- The class is final. Its instance fields start as Java's defaults (`null`, `0`, `false`), and `:post-init` sets them. Before the superclass constructor runs, a constructor of its own runs only `:init`, which computes that constructor's arguments and can't see the object. Static fields can be set by `:static-init`, which runs once per process: a new fn given on a redefinition runs only if the class hasn't been initialized yet, and a class whose initializer failed stays failed. A static method needs its full JVM name.
- The static initializer is a native `<clinit>`. champaca runs it, but HotSpot ignores the native flag on a `<clinit>` and refuses such a class file (`ClassFormatError: Absent Code attribute`), so the bytes are of no use outside champaca. The same goes for a constructor of its own, which is a native `<init>`. Reflection shows it without the `native` modifier, as Java would.
- Its methods are native methods, so reflection reports them with the `native` modifier, and they carry no generic signatures or `throws` lists. Annotations go on the class, its fields, methods and constructors, but not on parameters, and not on types (`TYPE_USE` annotations on a field or method are refused). A `@Repeatable` annotation is given once, or through its container.
- A method name never covers a package-private method of the superclass. A full JVM name with the same signature makes a public method, which overrides it only when the class is in the superclass's package, as on the JVM. A name in one of the JDK's packages is refused.
- When a method name has overloads that are final and others that aren't, the name covers the ones that aren't, and the final ones keep their bodies.
- Java code can't be compiled against the class, since it exists only at run time. Java reaches it through an interface or superclass it knows, through reflection, or through `Class.forName`.
- A class from the classpath with the same name that hasn't been loaded yet is never loaded afterwards, because the name already belongs to the jolt class. One that has been loaded makes `define-class` refuse the name.
- The class isn't kept in the startup cache. Each process defines it again, and its constructors are compiled again on their first call.

## Speed

The startup cache makes boot quick, and plain computation now runs within a few times of the JVM: `test/java/Bench.java` spends about 0.17 s computing what the JVM does in about 0.04 s. Calls, allocation, `try` blocks and synchronization cost several to many times more than on the JVM ([performance](performance.md#the-generated-code) has the numbers). The startup cache still slows a little as generations pile up (a cache filled by the whole test suite costs a warm `Hello` a few tens of milliseconds), though `state.img` entries now parse only when a run touches their class. Memory use is high: a warm Spring Boot start peaks at about six times the RSS HotSpot's does, and a cold one at about thirteen times ([bench/README](../../bench/README.md)).

## Other gaps

- The module path (`-p`, `-m`) takes modular jars, exploded modules and automatic modules (a jar with no `module-info.class`), but not `.jmod` files. A multi-release jar's classes are its base ones, on the module path as on the class path. A module path class's stack frame leaves out HotSpot's `module/` prefix (`app.Main.main(Main.java:7)` for `app/app.Main.main(...)`), and a missing class's `NoClassDefFoundError` trace has no line in the frame naming it and no loader frames under its cause, as for any class that isn't there. A module's resource URL is written `jar:file:/...` where HotSpot writes `jar:file:///...` (a non-ASCII path isn't percent-encoded either, and a directory's URL has no trailing slash), and `Class.forName` of a module path class through the boot loader proper names it slashed in its `ClassNotFoundException`. `MethodHandles.Lookup` doesn't check module access, so `findStatic` on a class in a package that isn't exported to the caller succeeds where HotSpot throws `IllegalAccessException` (the same holds for JDK classes). `init!` takes no module path.
- An [app bundle](app-bundles.md) runs only on the OS and architecture it was built on, since its compiled code is Chez machine code. Installed read-only with no writable home (or `CHAMPACA_USER_CACHE_DIR=off`), it compiles whatever its training run didn't reach on every run, because it has nowhere to save; with one, it keeps that in a cache of its own there. And `jdeps` can't see a module a program reaches only by name (`jdk.charsets` and `jdk.localedata` always go in; anything else needs `--add-modules`).
- A lambda's class lists the interface method it implements, public, as the JVM's does, and `Method.invoke` runs it (`test/java/LambdaReflectCheck.java`). Its declared fields differ: it has one private field holding the closure, where the JVM's has one per captured value.
- A lambda's class has an ordinary name (`champaca.$$Lambda$...`, which holds `$$Lambda` as the JVM's do, so a framework's check for it works), so `Class.forName` and `loadClass` find it by that name. The JVM's lambda classes are hidden, their names hold a `/`, and neither finds them. A failed cast of a lambda, or of an annotation (a generated class here, a `Proxy` on the JVM), names that class and puts it in the boot loader's unnamed module, where HotSpot's message names its hidden class or `jdk.proxyN.$ProxyN`.
- `java.nio.file` needs macOS, or Linux with glibc 2.33 or newer, on arm64 or x86_64. The file natives read `struct stat`, `struct dirent`, `struct flock` and `struct statvfs` through a table of offsets measured on each of those systems, and call `stat`, which glibc only exports itself since 2.33 (RHEL 8 and Debian 11 are older). On anything else, a BSD, musl or an older glibc, `UnixNativeDispatcher.init` throws `UnsupportedOperationException` instead of guessing. Only Ubuntu 26.04 (glibc 2.43) has been tested. `java.io` streams and `RandomAccessFile` don't depend on those layouts and work anywhere libc does. On Linux the birth time comes from `statx`, as the JVM's does.
- Linux's container support is off, as with `-XX:-UseContainerSupport`: inside a container champaca reports the host's memory and processor count, where the JVM reports the container's limits.
- File watching works on macOS, where the JDK's `WatchService` polls in plain Java, but not on Linux, where it needs inotify natives champaca doesn't have yet.
- A `float` is held as a Scheme double, so a signaling NaN's bits don't survive: `Float.floatToRawIntBits(Float.intBitsToFloat(0x7fa00001))` is `0x7fe00001` here, as is an int written into a `float[]` through a memory segment and read back, where the JVM keeps `0x7fa00001`. Doubles keep every NaN payload.
- `available()` on a pipe or a terminal is 0, where the JVM asks the kernel how much is waiting.
- A thread waiting for a `FileChannel` lock isn't woken when another thread closes the channel: the wait is restarted after the wake signal, where the JVM gives it up, so it ends when the lock is granted and finds the channel closed. Blocked reads, writes and accepts on sockets, channels and FIFOs do wake.
- A class that code names is looked for when the method naming it is first translated, the whole method at once, where the JVM resolves each reference when its instruction first runs. An `ldc` of a class (a `Foo.class` literal) is the exception: it resolves when it runs, through the defining loader of the class whose code it is, as on the JVM. A class that isn't there then makes that instruction throw `NoClassDefFoundError` when it runs, as on the JVM, but one that only becomes loadable later (a loader that registers it after the method's first call, a class file written meanwhile) is never seen by that method, and a loader of the program's own is asked through `loadClass` for every class such a method names, branches that never run included. A small method of the caller's own class (40 bytecode bytes or fewer, with no calls, loops or exception handlers, called directly: static, private or final) is compiled into its caller, so the classes it names are looked for when the caller is first translated, before the small method is ever called; `CHAMPACA_BT=1` turns that inlining off. A loader's error other than `ClassNotFoundException` is kept for the name and thrown by each instruction that names it, as the JVM repeats a failed resolution's error.
- A class that exists but champaca can't load (an opcode the translator lacks, a superclass that is missing) throws `NoClassDefFoundError` naming the cause from `Class.forName` and `loadClass`, as a class the JVM can't define throws a `LinkageError`. A class file that doesn't parse at all is the JVM's `ClassFormatError` instead, from those and from any instruction that needs the class, every time it runs. A file cut short and a wrong magic number carry HotSpot's messages, and any other parse failure champaca's own (`test/java/ClassFormatCheck.java`). It used to come back as `ClassNotFoundException`, so a library that probes for an optional class and catches only that exception took its fallback where it now stops with the cause; one catching `Throwable` or `LinkageError` goes on as before.
- Resources from the JDK's own modules can be read as streams but have no URL: `getResource` answers `file:` and `jar:` URLs for the classpath only. So a class loader of the program's own with no parent finds no JDK resource through `getResource` where the JVM gives a `jrt:` URL from the boot loader, and the platform loader answers `getResourceAsStream` for the JDK's resources but `getResource` and `getResources` with nothing. `-jar` with no jar gives the JVM's error and status but not its full usage text.
- System properties are the JVM's except where they name the VM: `java.vm.name`, `java.vm.vendor` and `java.vm.version` say champaca, HotSpot's own (`java.vm.info`, `sun.management.compiler`) are absent, `jdk.reflect.useNativeAccessorOnly` is set, and `java.library.path` is empty unless a `-D` option sets it, since no JNI code runs. The default locale comes from where the JDK gets it: on macOS your first preferred language in System Settings (`LANG` isn't read there, as on the JVM), on Linux `LC_MESSAGES` and `LC_CTYPE`, with a locale that isn't installed counting as `en_US`. Of a Linux locale's `@modifier` only a script (`@latin`, `@cyrillic`) is read, and the JDK's legacy aliases aren't applied. `java.io.tmpdir` is macOS's per-user temporary directory, and `sun.java.command` is set when `champaca.main` starts the program.
- `champaca.main` reads `-D`, `-cp` (and its spellings), the assertion switches, `-server`/`-client`, `-Xss`, `--enable-preview`, the module options (`--add-modules`, `--enable-native-access`, `--illegal-native-access`, `--add-opens`, `--add-exports`, `--add-reads`, `--limit-modules`) and the version switches. Heap sizes (`-Xmx`, `-Xms`, `-Xmn`), `-Xshare:`, `-XX:` flags, `-verbose`, `-Xlog` and HotSpot's execution-mode and diagnostic `-X` options are ignored with a warning on stderr: the heap is Chez Scheme's, which grows as it needs to, with no switch for its size, and there's no HotSpot logging to turn on.
- Weak and phantom references are cleared by Chez's collector, and the JDK's Reference Handler thread queues them, so `WeakHashMap` drops keys nobody holds, a `Cleaner`'s action runs, and a direct buffer's native memory is freed once the buffer is unreachable. The queueing happens within about 100 ms of the collection that cleared the referent (`test/java/ReferenceCheck.java`, and upstream's `aaa/referenceprocessing`). Finding the cleared references looks at every live weak or phantom reference with a queue each time, so a program holding hundreds of thousands of them (a huge `WeakHashMap`) pays for the scan after collections. A soft reference keeps its referent for good, which the JVM is allowed to do until memory runs short. `finalize()` never runs, as on a JVM started with finalization disabled. `System.gc()` runs a full collection, and other threads wait for it.
- A thread's stack is bounded at 1 MB, the JVM's default, or at `-Xss`'s size (`JOLT_STACK_LIMIT` decides when set; the jolt API leaves jolt's own bound alone). Past it a `StackOverflowError` is thrown, which a program can catch as on the JVM. jolt finds the overflow at a collection, so the stack can pass the bound before it does. Champaca's frames are smaller than HotSpot's, so the same bound holds a deeper recursion, about 52,000 frames of a small method against HotSpot's 42,000. Since the bound is checked at collections, a recursion of small frames can run millions deep before it's found. Unwinding that through a `try` in every frame that does work in its `finally` costs time quadratic in the depth, because each escape from a handler's region measures the winder lists: such a recursion took minutes to overflow. A plain recursion overflows in a quarter of a second. A method champaca compiles isn't held to the bound, since the compiler's recursion is champaca's work, not the program's (`BigLiteralCheck`). Every other option (`--patch-module`, `--upgrade-module-path`, `-Xbootclasspath/a:`, `-javaagent` among them) stops with `Unrecognized option`, and the `CLASSPATH` environment variable isn't read ([running Java programs](running-java-programs.md)).
- The Vector API (`jdk.incubator.vector`, with `--add-modules`) gives HotSpot's results but isn't accelerated: champaca answers the few questions it asks the VM (the vector width, 128 bits on arm64 as HotSpot has it there and 256 on x86_64 whatever the CPU) and every operation runs on the Java fallback the JDK keeps for each intrinsic, lane by lane, with a vector object per step. Summing 100,000 ints that way took 30 ms against 0.18 ms for a plain loop, where on HotSpot the two are about equal. Operations that view lanes as another type (`reinterpretAs*`, `castShape`, `viewAs*`, `test(IS_NAN)`) and loads and stores through a `MemorySegment` work, through the JDK's memory segment code (`test/java/VectorCheck.java`). The vector math library (SLEEF, SVML) isn't loaded, so `SIN`, `EXP` and the rest use the JDK's Java versions, as HotSpot does when the library is missing. Where HotSpot's compiled code calls the library instead, its results for those operations can differ from champaca's in the last place. They matched in VectorCheck's rows on an arm64 Mac.
- `jsr` and `ret` run in a class file of any version. HotSpot's verifier refuses them from version 51 (Java 7) on, and champaca doesn't verify bytecode, so such a class runs here where the JVM throws `VerifyError`.
- A class naming a module outside the boot layer fails one instruction at a time, when that instruction runs. HotSpot's verifier loads some named classes while it links the class naming them, a catch clause's type among them, so there the whole class fails with `NoClassDefFoundError` before any of it runs. champaca doesn't verify bytecode: such a class runs, and a catch clause naming an out-of-layer class never matches. JDK code compiled by an earlier run keeps what it resolved, but a JDK module names only modules it requires, and the boot layer holds those, `requires static` ones apart.
- A lone `--add-opens=`, with nothing after the `=`, stops the program with the JDK's "Unable to parse" error. HotSpot runs the program: it takes the boot layer from its class data sharing archive, which never reads the option, and with `-Xshare:off` it fails as champaca does.
- `sun.misc.Unsafe` runs with `sun.misc.unsafe.memory.access=allow`, so Caffeine and Guava run without the JDK's warning on stderr.
- Class loaders answer as on the JVM for your classes, the JDK's and the built-in loaders: your classes report the application loader and sit in its unnamed module, a JDK class reports the loader its module is defined to (null for `java.base`, the platform loader for `java.sql`), a class a loader defined at run time reports that loader, and the built-in loaders see what the JVM's do: the application loader everything, the platform loader the JDK, the boot loader (a null loader in `Class.forName`) its own modules only. A lambda's class is the exception: it reports a null loader and sits in the boot loader's unnamed module, where the JVM gives it the capturing class's loader and module, since champaca shares one generated class per interface between your call sites and the JDK's. So `lambda.getClass().getModule() == Main.class.getModule()` is false here and true on the JVM, and a lambda's class answers `desiredAssertionStatus` as a JDK class would (`-esa`, not `-ea`), where the JVM follows the capturing class; its body's asserts are the capturing class's own, so which asserts run is the same; an unnamed module exports everything, so reflection across the two still works. A `module-info` on your classpath is never read: everything you give champaca is unnamed, with no module path and no checks between your own packages. The JDK's own modules are named and their exports and opens are checked, as on the JVM ([jars-and-modules](jars-and-modules.md#jdk-modules)).
- A `NullPointerException` raised in champaca's own Scheme code, which stands in for some of the JDK's Java (the method handle layer, for one), has a `null` message where the JVM's might describe the failing bytecode. One the program's or the JDK's bytecode raises carries the JVM's message, such as `Cannot invoke "String.length()" because "<local1>" is null` (`test/java/NpeCheck.java`).
