# Limitations

Champaca is a spike. It runs the JDK's own code, but only along the paths its tests and the eight checked libraries (commons-lang3, gson, jsoup, Jackson, Caffeine, Guava, SLF4J, SnakeYAML) have exercised. Code outside those paths can hit a missing native or one of the shortcuts below. This page lists the ones known so far, roughly in the order a real program meets them.

## Threads take turns

Threads work, but they don't run in parallel. Each Java thread is a real Chez thread, and one global lock lets only one of them run Java code at a time ([how-it-works](how-it-works.md#threads)). A program that uses threads for correctness (a background worker, a producer and a consumer, an executor) behaves as on a JVM. One that uses them for speed gets none.

Some details follow from that. A thread that loops without calling anything gives the lock up every thousand backward branches once another thread is waiting, so a spin-wait ends, but a long recursive computation with no loop in it can keep the others waiting until it returns. A thread waiting on I/O gives the lock up: reading standard input, a pipe, a FIFO or a terminal, writing to a full pipe, opening a FIFO, `Files.copy` from a pipe, and taking a blocking file lock (`test/java/BlockingIoCheck.java`). Writes to standard output and error still hold it, so a program whose output pipe fills up stops until the reader catches up. Closing a socket, a channel or a FIFO from another thread wakes a thread blocked on it, with the JVM's exception (`SocketException: Socket closed`, `AsynchronousCloseException`), and interrupting a thread blocked in a channel read gives `ClosedByInterruptException` (`test/java/SocketCheck.java`). A thread waiting for a blocking file lock is the exception: see [other gaps](#other-gaps). VarHandle and `Unsafe` memory-ordering modes all behave alike, which is safe for the same reason. Virtual threads need continuations, which aren't here, so `Thread.ofVirtual()` is unsupported. `getState` reports `RUNNABLE` for a thread that is blocked or waiting.

## `invokedynamic` and method handles

Both work, with a few gaps. The bootstraps javac emits are compiled directly: lambdas, records, string concatenation and pattern switches. Any other bootstrap method runs for real, once per call site ([how-it-works](how-it-works.md#method-handles)).

Method handles come from the `Lookup.find*` and `unreflect*` methods, and `invokeExact`, `invoke`, `invokeWithArguments`, `asType`, `bindTo`, `asSpreader`, `asCollector` and the `MethodHandles` combinators work on them: `zero`, `empty`, `constant`, `identity`, `insertArguments`, `dropArguments`, `filterArguments`, `filterReturnValue`, `foldArguments`, `collectArguments`, `guardWithTest`, `permuteArguments`, `explicitCastArguments`, `catchException`, `throwException`, `tryFinally`, the array element handles and the three invokers, with the JVM's conversions and exception texts (`test/java/MethodHandleCombinatorCheck.java`). The loop builders (`countedLoop`, `whileLoop`, `doWhileLoop`, `iteratedLoop`, `loop`) still run the JDK's own code, which fails on these handles, usually with an `AbstractMethodError` for `MethodHandle.rebind`. `invokeExact` doesn't check that the call matches the handle's type exactly. It converts the arguments as `invoke` would, so a call the JVM rejects with `WrongMethodTypeException` runs here (`exactInvoker` does check). `asType` refuses an impossible conversion when the handle is built, with the JVM's `WrongMethodTypeException` text. `explicitCastArguments` converts the way `asType` does, so it won't narrow a `long` to an `int` as the JVM's does. Lookups don't check access either. A pattern switch label that javac builds from a dynamic constant other than a primitive class or an enum constant fails to translate.

VarHandles work too: `findVarHandle`, `findStaticVarHandle`, `unreflectVarHandle`, `arrayElementVarHandle` and `byteArrayViewVarHandle`, which is what `java.util.concurrent.atomic` and `ConcurrentHashMap` need. Each supports the access modes the JVM's would, and the rest throw `UnsupportedOperationException`. So a `final` field is read-only, a `float` has no bitwise updates, and a `byte[]` view takes only plain `get` and `set`, as on JDK 25. A call site's types are converted as `asType` would, which means widening, boxing and unboxing but never narrowing (an `int` passed for a `short` throws `WrongMethodTypeException`), and a handle from `withInvokeExactBehavior` rejects a call whose types differ with `WrongMethodTypeException`. The six coordinate combinators work (`filterValue`, `filterCoordinates`, `insertCoordinates`, `permuteCoordinates`, `collectCoordinates`, `dropCoordinates`), with the JVM's construction-time checks and messages; a derived handle supports the modes its target does. Their filters aren't screened for checked exceptions: the JVM refuses a direct handle whose method declares one and wraps any other handle so a checked exception becomes `IllegalStateException`, and champaca does neither. `byteBufferViewVarHandle` is missing.

## Reflection

Methods, fields, constructors, `Method.invoke`, `newInstance` and field get and set work, and so do annotations with their defaults, generic signatures, and member, local and anonymous classes. Record components, parameter names (real ones when the class was compiled with `javac -parameters`, else `arg0`, `arg1` as on the JVM), checked-exception lists and type annotations match the JVM's too, which is what Jackson needs to bind records. An annotation is an instance of a generated class rather than a `java.lang.reflect.Proxy`, so `Proxy.isProxyClass` says false for it, but its `toString`, `equals` and `hashCode` are the JDK's own. Field access through reflection ignores access control. `Class.getPackage` gives one `Package` per name. A classpath package carries the version attributes of the manifest of the jar its first loaded class came from, as the JVM's class loaders define it, so a package split over two jars reads the same as on the JVM. A JDK package belongs to its named module, so it reports `isSealed` and no version, as on the JVM. Some differences remain. Sealing isn't enforced, so a sealed package split over two jars loads instead of throwing `SecurityException`. A jar whose manifest the JDK would refuse gets a warning on stderr and its classes load without version information, where the JVM fails to load them. A lambda's class is `champaca/Lambda$...`, shared by every call site with the same interface, so its package is `champaca` rather than its caller's. `Package.getPackage(String)` and `Package.getPackages()` find a JDK package of the boot loader once a class of it has loaded, as on the JVM, and it's the same `Package` that `Class.getPackage` gives. A package of your own classes isn't found that way, though, and `ClassLoader.getDefinedPackage` finds none of your packages either. A package of a platform-loader module such as `java.sql` is found only once something has called `getPackage` on one of its classes, where the JVM's platform loader defines it as it loads the first class. Nests come from the `NestHost` and `NestMembers` attributes, checked as JVMS 5.4.4 asks (the host loads, is in the same package and lists the class), and a hidden class defined as a nestmate joins its lookup class's nest. So `getNestHost`, `getNestMembers` and `isNestmateOf` answer as on the JVM, and a class file older than Java 11 is its own nest host there too. `getDeclaredClasses` still returns an empty array.

## Native code

A JDK library load (`zip`, `net`, `management` and so on) is a no-op, because those natives are Scheme here. A Java library's own JNI code can't load: `System.loadLibrary` throws `UnsatisfiedLinkError` for any library the JDK doesn't ship, as the JVM does for one that isn't on `java.library.path`. A native champaca hasn't written yet throws `UnsatisfiedLinkError` too ([debugging](debugging.md#a-missing-native)), so a library's try/catch around an optional feature works as on the JVM, and a program that needs the native stops there. The ones known to be missing, roughly in the order a library meets them:

- Sockets are TCP over IPv4: `Socket`, `ServerSocket`, blocking `SocketChannel`s, `HttpURLConnection` and `InetAddress` lookups work, through libc. The JDK is told IPv6 is unavailable: a host name is looked up for its IPv4 addresses only, so a host with both kinds works through those and an IPv6-only host is an `UnknownHostException`, and a literal IPv6 address such as `::1` given to connect or bind throws `SocketException: Protocol family unavailable` where the JVM connects. Selectors work, and with them non-blocking channels and `java.net.http.HttpClient`. `bb test` checks HTTP/1.1 against a server in the same process; HTTPS, over HTTP/1.1 and over HTTP/2 (the response reported `HTTP_2`, so the server negotiated it), and `HttpsURLConnection` were checked by hand against a public site (`https://example.com`, 2026-10-25), since the tests need no network. In two warm runs that day the first HTTPS request took 3.0 and 3.1 s, against 0.2 to 0.4 s on the JVM, and a second client's request 0.4 to 0.5 s. UDP works over IPv4 (`DatagramSocket`, `DatagramChannel`), but a socket can't join a multicast group (`MulticastSocket.joinGroup` and `DatagramChannel.join` stop at a missing native). `NetworkInterface` lists only the interfaces that have an IPv4 address, since IPv6 is off: on a Mac the JVM also lists `utun`, `awdl0` and `llw0`, which carry IPv6 addresses only. A Linux alias such as `eth0:1` is listed as an interface of its own, where the JVM makes it a virtual sub-interface of `eth0`. `InetAddress.isReachable` always tries TCP port 7, as the JDK does when it can't open a raw socket; run as root, the JVM sends an ICMP echo instead, so a host that drops port 7 silently but answers ping is reachable there and not here. Pending urgent data isn't discarded, and the extended options of `jdk.net` report themselves unsupported.
- Child processes start through `posix_spawn` whatever `jdk.lang.Process.launchMechanism` says, so the JDK's `jspawnhelper` never runs; what a program can see matches the JVM ([how-it-works](how-it-works.md#natives)). `ProcessHandle.Info` is empty: its command, arguments, user, start time and CPU time are all unknown. With no start times, a `ProcessHandle` can't tell its process from a later one that reused the pid, so `destroy` on a handle from `ProcessHandle.of` whose process is gone signals whatever runs under that pid now, where the JVM refuses; a `Process` is safe, since it stops signalling once it has seen its child exit. `ProcessHandle.children()` and `descendants()` stop at a missing native. Under Docker's x86_64 emulation on an arm64 Mac, a script without `#!` exits 127 instead of running through `/bin/sh`, because the emulated `posix_spawn` doesn't report that `exec` failed; natively it runs.
- A stack trace lists translated methods only: a native champaca wrote in Scheme has no frame, where the JVM prints one as `Native Method`. JDK frames carry no line numbers, only the file, since the startup cache keeps no inspector information for JDK code ([performance](performance.md#exception-handlers)). Reflection's own frames differ in name (`DirectMethodHandleAccessor$NativeAccessor.invoke` here, `DirectMethodHandleAccessor.invoke` on the JVM). `Thread.getStackTrace()` on another thread stops at a missing native, `Thread.getAllStackTraces()` gives every live thread but only the current one's frames (the others' are empty arrays, which its contract allows), and `StackWalker`'s `SHOW_HIDDEN_FRAMES` option doesn't bring the hidden frames back.
- `java.management`: the Runtime, Memory, OperatingSystem and ClassLoading beans answer, and `ThreadMXBean` counts and lists threads. Its CPU times are measured for any live thread the way HotSpot measures them (`thread_info` on macOS, the thread's CPU clock and `/proc` on Linux). The thread lists hold the threads Java started and `main`: a jolt thread that called in isn't listed, and there are no JVM system threads such as `Reference Handler`. `ThreadInfo` stops at `getThreadInfo1` and thread dumps at `dumpThreads0`; `findDeadlockedThreads` says it's unsupported, as the JDK does when the VM reports no support, while `findMonitorDeadlockedThreads` stops at its native; the garbage collector and memory pool lists are empty. Memory figures are Chez's own heap counters, the same ones `Runtime.totalMemory()` and `freeMemory()` report. The operating system bean is `jdk.management`'s, as on the JVM: its host CPU counts and process CPU time are real, and its memory and swap sizes, CPU loads and file descriptor counts are -1, which its contract allows for what isn't measured.
- Classes defined at run time (`ClassLoader.defineClass`, `Lookup.defineClass` and `defineHiddenClass`, `java.lang.reflect.Proxy`) join the one class table, so a name can be defined once: a second loader defining a class of the same name gets `LinkageError` where the JVM gives each loader its own, and the application loader never loads the classpath's copy of a name another loader defined.

## The calling API

- `init!` takes effect once per process. A second call, with a different `:classpath` or not, does nothing.
- Until `save-cache!` runs, each JDK method the process compiles keeps its generated source in memory (a few KB per method) so a save can write it. A long-lived program should call `save-cache!` once its working set is warm, which also empties that list.
- The user classpath is searched before the JDK's modules, the reverse of Java's order.
- Every conversion copies. A Java method that changes a collection you passed it changes the copy, and a big collection is copied again on each call ([data-conversion](data-conversion.md#conversions-copy)).
- A vector passed to a plain `Object` parameter becomes an array, not a `List`.
- A Java object prints as `#object[:object]` in jolt. Use `ldk/to-string`.
- A Java string can hold a lone surrogate (half of a UTF-16 pair) and a jolt string can't, so one comes back to jolt with U+FFFD in its place. Inside Java nothing is lost: string constants, concatenation and `switch` keep the code units exactly.

## Speed

The startup cache makes boot quick, and plain computation now runs within a few times of the JVM: `test/java/Bench.java` spends about 0.17 s computing what the JVM does in about 0.04 s. Calls, allocation, `try` blocks and synchronization cost several to many times more than on the JVM ([performance](performance.md#the-generated-code) has the numbers). Classes from a directory on the classpath compile on every run, since only the JDK's and jars' classes are cached. The startup cache still slows a little as generations pile up (a cache filled by the whole test suite costs a warm `Hello` a few tens of milliseconds), though `state.img` entries now parse only when a run touches their class.

## Other gaps

- `java.nio.file` needs macOS, or Linux with glibc 2.33 or newer, on arm64 or x86_64. The file natives read `struct stat`, `struct dirent`, `struct flock` and `struct statvfs` through a table of offsets measured on each of those systems, and call `stat`, which glibc only exports itself since 2.33 (RHEL 8 and Debian 11 are older). On anything else, a BSD, musl or an older glibc, `UnixNativeDispatcher.init` throws `UnsupportedOperationException` instead of guessing. Only Ubuntu 26.04 (glibc 2.43) has been tested. `java.io` streams and `RandomAccessFile` don't depend on those layouts and work anywhere libc does. On Linux the birth time comes from `statx`, as the JVM's does.
- Linux's container support is off, as with `-XX:-UseContainerSupport`: inside a container champaca reports the host's memory and processor count, where the JVM reports the container's limits.
- File watching works on macOS, where the JDK's `WatchService` polls in plain Java, but not on Linux, where it needs inotify natives champaca doesn't have yet.
- `Files.getFileStore` and the other mount queries have no natives yet.
- `available()` on a pipe or a terminal is 0, where the JVM asks the kernel how much is waiting.
- A thread waiting for a `FileChannel` lock isn't woken when another thread closes the channel: the wait is restarted after the wake signal, where the JVM gives it up, so it ends when the lock is granted and finds the channel closed. Blocked reads, writes and accepts on sockets, channels and FIFOs do wake.
- `Unsafe.copyMemory` between native memory and a `float[]` or `double[]` fails, since those arrays hold Scheme flonums rather than bytes.
- A class that code names is looked for when the method naming it is first translated, the whole method at once, where the JVM resolves each reference when its instruction first runs. A class that isn't there then makes that instruction throw `NoClassDefFoundError` when it runs, as on the JVM, but one that only becomes loadable later (a loader that registers it after the method's first call, a class file written meanwhile) is never seen by that method, and a loader of the program's own is asked through `loadClass` for every class such a method names, branches that never run included. A loader's error other than `ClassNotFoundException` is kept for the name and thrown by each instruction that names it, as the JVM repeats a failed resolution's error.
- A class that exists but champaca can't load (an opcode or attribute the translator lacks, a superclass that is missing) throws `NoClassDefFoundError` naming the cause from `Class.forName` and `loadClass`, as a class the JVM can't define throws a `LinkageError`. It used to come back as `ClassNotFoundException`, so a library that probes for an optional class and catches only that exception took its fallback where it now stops with the cause; one catching `Throwable` or `LinkageError` goes on as before.
- Resources from the JDK's own modules can be read as streams but have no URL: `getResource` answers `file:` and `jar:` URLs for the classpath only. So a class loader of the program's own with no parent finds no JDK resource through `getResource` where the JVM gives a `jrt:` URL from the boot loader, and the platform loader answers `getResourceAsStream` for the JDK's resources but `getResource` and `getResources` with nothing. `-jar` with no jar gives the JVM's error and status but not its full usage text.
- System properties are the JVM's except where they name the VM: `java.vm.name`, `java.vm.vendor` and `java.vm.version` say champaca, HotSpot's own (`java.vm.info`, `sun.management.compiler`) are absent, `jdk.reflect.useNativeAccessorOnly` is set, and `java.library.path` is empty since no JNI library loads. The default locale comes from where the JDK gets it: on macOS your first preferred language in System Settings (`LANG` isn't read there, as on the JVM), on Linux `LC_MESSAGES` and `LC_CTYPE`, with a locale that isn't installed counting as `en_US`. Of a Linux locale's `@modifier` only a script (`@latin`, `@cyrillic`) is read, and the JDK's legacy aliases aren't applied. `java.io.tmpdir` is macOS's per-user temporary directory, and `sun.java.command` is set when `champaca.main` starts the program.
- `sun.misc.Unsafe` runs with `sun.misc.unsafe.memory.access=allow`, so Caffeine and Guava run without the JDK's warning on stderr.
- Class loaders answer as on the JVM for your classes, the JDK's and the built-in loaders: your classes report the application loader and sit in its unnamed module, a JDK class reports the loader its module is defined to (null for `java.base`, the platform loader for `java.sql`), a class a loader defined at run time reports that loader, and the built-in loaders see what the JVM's do: the application loader everything, the platform loader the JDK, the boot loader (a null loader in `Class.forName`) its own modules only. A lambda's class is the exception: it reports a null loader and sits in the boot loader's unnamed module, where the JVM gives it the capturing class's loader and module, since champaca shares one generated class per interface between your call sites and the JDK's. So `lambda.getClass().getModule() == Main.class.getModule()` is false here and true on the JVM; an unnamed module exports everything, so reflection across the two still works. A `module-info` on your classpath is never read: everything you give champaca is unnamed, with no module path and no checks between your own packages. The JDK's own modules are named and their exports and opens are checked, as on the JVM ([jars-and-modules](jars-and-modules.md#jdk-modules)).
- A `NullPointerException` raised in champaca's own Scheme code, which stands in for some of the JDK's Java (the method handle layer, for one), has a `null` message where the JVM's might describe the failing bytecode. One the program's or the JDK's bytecode raises carries the JVM's message, such as `Cannot invoke "String.length()" because "<local1>" is null` (`test/java/NpeCheck.java`).
